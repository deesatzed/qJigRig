# Token-cost bound investigation

**Status: non-authorizing candidate; hosted billing remains unresolved.** No inference calls were made for this investigation.

OpenRouter's [provider-routing documentation](https://openrouter.ai/docs/guides/routing/provider-selection) describes `provider.max_price` as a filter on acceptable provider prices, with prompt and completion values in dollars per million tokens. Its [pricing page](https://openrouter.ai/pricing) describes model input and output billing at provider rates and says BYOK inference is billed directly by the provider. These sources support the inference that a routing ceiling and a catalog token rate are alternative limits on the same token-price category, rather than separate token charges. They do not prove account-specific billing, metadata completeness, provider enforcement, a future price, or the maximum amount of any separately billed feature.

The candidate calculation takes the greater of catalog and routing ceiling for prompt and completion and conservatively adds the listed cache read/write rates. This bounds the listed token categories under the stated assumptions; it is not a complete invoice guarantee. OpenRouter's [plugin documentation](https://openrouter.ai/docs/guides/features/plugins/overview) also says account administrators can prevent request-level plugin overrides. A request asking to disable a plugin therefore does not establish the account's effective configuration. BYOK and auxiliary charges remain separate unknowns.

`estimate_candidate_hosted_attempt` now binds this calculation to the exact request digest, versioned routed wire-body digest, selected catalog data, route and estimated input/output limits. The existing combined preflight exposes it as a comparison for routed calls, while retaining the existing additive reservation and explicitly returning `hosted_authorized=false` and `billing_assurance=unknown`. The candidate is not a `CallReservation`, is not used by the goal ledger, and cannot enable the hosted transport.

Before a lower bound can govern paid calls, finish the durable cost-policy and work-slot binding, full billing/category and account checks, refreshed pricing and overage recovery. Demonstrate all of them through the actual guarded dispatch path with appropriate failure and restart tests. No arithmetic change alone makes the campaign affordable or establishes that a token estimate, quota or output cap is adequate.
